part 2

Backend / frontend parity

Fixed — wishlist never reached the real backend

Wrong path, wrong port, wrong response shape
fixed

The wishlist service called {wishlistApiUrl}/api/v1/wishlist. The real backend route is /wishlist — no /api/v1 prefix ever existed. Confirmed live: hitting any wrong or nonexistent path on techshop-wishlist with a valid token returns 401, not 404 — Spring Security's catch-all anyRequest().authenticated() rejects before routing gets a chance to 404. That's exactly why the code's own comment concluded "the backend rejects valid tokens" and built a permanent fallback around it. Dev environment also pointed wishlistApiUrl at port 8085 — the notification service, not wishlist (8086).

Once the path was fixed, a second problem surfaced: the response shape never matched either. The frontend expected a flat {productId, productName, productPrice, quantity}[]; the real backend returns {id, userId, items: [{id, product: FullProduct, addedAt}], createdAt}.

before`${wishlistApiUrl}/api/v1/wishlist` dev port: 8085 (notification) data: WishlistItemResponse[]
now`${wishlistApiUrl}/wishlist` dev port: 8086 (wishlist) data: mapped from real shape

Fixed the URL and port, and added a mapping adapter inside WishlistService so every downstream consumer — the wishlist page, badge, and button components — kept the flat shape they already expect. Nothing outside the service changed.

This bug meant the real wishlist table was never populated by an actual user action — everything ran on a client-side mock. It directly blocked the price-drop-notification feature from last session, since the subscriber lookup reads from that same table.

Live: registered two test users, wishlisted a real product, confirmed GET/POST/DELETE hit the real DB. Full frontend suite green (54/54 files, both isolated and default runs) after updating the two spec files that hardcoded the old URL/shape.

Fixed — admin stock edit returned 405 on every save

No endpoint matched what the admin UI was calling
fixed

The admin products page sends PUT /api/products/{id}/stock with {quantity} — an absolute value. The only endpoint at that path was PATCH /api/products/{id}/stock, taking a relative {quantityDelta} and gated by an internal API key — that one exists for the order service to decrement stock on checkout, not for a browser admin panel.

live before fixPUT .../18/stock {"quantity": 42} → 405 Method Not Allowed
live after fixPUT .../18/stock {"quantity": 42} → 200, stock: 42

Added a new admin-only PUT /api/products/{id}/stock endpoint that sets stock directly. The internal PATCH delta endpoint used by checkout is untouched.

Live: admin token → 200 and stock updated; customer token → 403; reverted the test edit. 6 new backend tests (service + controller, success/forbidden/unauthenticated/validation).

Reported, not fixed — two payment methods bypass the real backend

ROKET_LINE and INSTALLMENT checkouts are entirely fake
needs follow-up

order.ts's checkout() skips the real POST /api/orders/checkout call for ROKET_LINE and INSTALLMENT, with a comment claiming the backend doesn't support them yet. It does: RoketLinePaymentService and InstallmentPaymentService are both active @Service beans wired into PaymentProviderFactory, both fully covered by the 16-test PaymentProvidersTest. Only CARD is genuinely unsupported — it isn't even in the backend's PaymentMethod enum.

The frontend also names the field installmentPlan; the backend expects installmentDetails. So removing the skip alone wouldn't be enough — installment orders would submit with the detail silently dropped and get rejected.

Left this one alone. It's a real gap, but it's a checkout/money-flow change I can't fully verify without driving the actual UI (address forms, the installment modal, cart state) in a browser — worth its own focused pass rather than a same-sweep patch.

Everything else checked out

Every other endpoint the frontend calls — across auth, products, cart, orders, reviews, admin stats, notifications, and chat — matches a real backend route on method and path. The five internal, key-guarded, service-to-service endpoints (price-drop preference lookup, stock delta, rating update, wishlist subscribers, the dual-use user lookup) are correctly never called from the browser, as intended.
